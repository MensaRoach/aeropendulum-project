# Assignment 01 — I2C Bus Driver and MPU-6050 Library

**Goal:** make the board read live accelerometer and gyroscope data from the MPU-6050 over I2C.

**Files you will edit:** `DRIVERS/src/bus_i2c.c`, `DRIVERS/src/mpu6050.c`, and one new test app in
`APPS/`.

**Files you will not edit:** anything in `DRIVERS/inc/` (the API is fixed), anything in `BOARDS/`
(generated by CubeMX), and the `.ioc` file.

**Out of scope for this assignment:** `mpu6050_start_read`, `mpu6050_sample_ready`,
`mpu6050_get_sample`, `mpu6050_dropped_samples`, `i2c_bus_read_async`, and the four IRQ handlers.
Leave them exactly as they are. They are Assignment 02.

**Estimated effort:** 10–15 hours, spread over several sessions. Part A is the hard half.

## Before you start

### S1 — Get the register map document

The PDF already in `.docs/IMU/` is the **product specification**: electrical characteristics,
package dimensions, performance figures. It does not describe registers.

The register descriptions are in a **separate InvenSense document**, the *MPU-6000/MPU-6050 Register
Map and Descriptions*. Find it and put it in `.docs/IMU/`.

You cannot do Part B without it. Do this first.

- [ ] **Done when:** `.docs/IMU/` contains the register map document and you can find the chapter
      listing register addresses.

### S2 — Build and flash the existing firmware

```bash
cmake --preset NUCLEO-F401RE-Debug-Local
cmake --build .build/NUCLEO-F401RE-Debug-Local
```

Flash it with the VS Code `Debug / Flash NUCLEO-F401RE (Cortex-Debug)` launch configuration. The
board currently runs `APP_BLINKY`.

- [ ] **Done when:** LD2 blinks at 1 Hz. This proves your toolchain, wiring and flash path work
      before any of your own code is involved.

### S3 — Wire the sensor

I2C1 is on **PB6 (SCL)** and **PB7 (SDA)**. Power the MPU-6050 from 3.3V and share ground with the
Nucleo. Check whether your breakout board already has pull-up resistors on SDA and SCL — most do. If
it does not, add 4.7 kΩ from each line to 3.3V.

- [ ] **Done when:** the sensor is wired and you have written down which address its AD0 pin selects.

### S4 — Read the reference material

- The **I2C chapter of RM0368** (`.docs/MCU/rm0368-...pdf`), specifically the "Master transmitter"
  and "Master receiver" sections. These give the exact flag-by-flag sequences you must follow.
- The register map chapter listing **all** registers, so you know what exists before deciding what
  to configure.

## Part A — I2C bus driver (`DRIVERS/src/bus_i2c.c`)

This part has no sensor-specific behaviour at all. You are building a general-purpose I2C register
read/write for the STM32F4, and it should work with any I2C device.

> **Reference implementation available.** A previous version of this project had working I2C code.
> It is in git history:
>
> ```bash
> git show 11c4068^:APPS/src/mpu6050_telemetry.c
> ```
>
> Read it. Use it. It shows the correct flag sequences, which is the part that takes longest to get
> right from the reference manual alone. **But it has two defects you must fix rather than copy** —
> Task A5 and A7 tell you what they are.

### A1 — Millisecond timebase

Implement `I2C_DeadlineExpired()`.

The CubeMX startup code already runs SysTick at 1 kHz (see `LL_Init1msTick` in
`SystemClock_Config`). LL exposes a tick counter you can read.

```c
static bool I2C_DeadlineExpired(uint32_t start_ms, uint32_t timeout_ms);
```

Watch the wraparound: the tick counter is a `uint32_t` that eventually overflows. Subtracting
unsigned values in the right order handles this correctly; comparing them with `>` does not.

- [ ] **Done when:** the function returns `false` immediately after `start_ms` and `true` after the
      timeout has passed, including when the counter wraps.

### A2 — Bus recovery

Implement `i2c_bus_recover()`.

**Why this exists:** if the MCU resets in the middle of a read, the sensor can be left mid-byte,
holding SDA low and waiting for clock pulses that never come. The bus is then stuck before the
peripheral is even switched on, and no amount of peripheral configuration fixes it. The escape is to
drive the pins manually.

Sequence:

1. Reconfigure `scl_pin` and `sda_pin` as **general-purpose open-drain outputs** with pull-ups.
2. Drive both high. Wait briefly.
3. Toggle SCL up to 9 times, checking after each pulse whether SDA has gone high. Stop as soon as it
   has.
4. Generate a manual STOP condition: SDA low, then SCL high, then SDA high.
5. Reconfigure both pins back to alternate function using `bus->gpio_af`.

- [ ] **Done when:** the function returns `DRV_OK` if SDA is high at the end, and `DRV_ERR_BUS` if it
      is still low after 9 pulses.

> The old code in git history clocks a fixed 9 times and never checks whether it worked. Yours
> should check. A recovery routine that cannot report failure is a ritual, not a fix.

### A3 — Initialisation

Implement `i2c_bus_init()`.

**What CubeMX already did:** `MX_I2C1_Init()` configured the peripheral — timing, addressing mode,
duty cycle — and then **left it disabled**. `LL_I2C_Init()` ends with `LL_I2C_Disable()` and never
re-enables it. Enabling it is your job.

Steps:

1. Validate `bus` and `bus->instance` are not NULL. Return `DRV_ERR_PARAM` if either is.
2. Call `i2c_bus_recover()`. If it fails, return that failure and leave `initialised` false.
3. If `speed` differs from what CubeMX programmed, reconfigure it. (Look at `LL_I2C_ConfigSpeed`.)
4. Enable the peripheral.
5. Set `initialised = true`, return `DRV_OK`.

- [ ] **Done when:** a failed init leaves `initialised` false, and every transfer function returns
      `DRV_ERR_STATE` in that state. Add that guard to the transfer functions as you write them.

### A4 — Blocking write

Implement `i2c_bus_write()`.

The sequence for writing `len` bytes to a register:

```
START -> address+W -> register address -> data[0] .. data[len-1] -> STOP
```

Requirements:

- `bus` arrives as `void *` (the transport interface is address-agnostic). Cast it to `i2c_bus_t *`
  at the top.
- `dev_addr` is **7-bit and right-aligned**. Shift it left by one and add the read/write bit here,
  in exactly one place.
- Take a timestamp at the start. Every wait loop checks `I2C_DeadlineExpired()` and returns
  `DRV_ERR_TIMEOUT` rather than spinning forever.
- Return `DRV_ERR_PARAM` for a NULL `data` with non-zero `len`.

- [ ] **Done when:** writing to a nonexistent address returns an error within the timeout instead of
      hanging, and writing to a real device returns `DRV_OK`.

### A5 — Blocking read

Implement `i2c_bus_read()`.

The sequence for a register read is a **combined transfer** — the direction changes mid-transaction
without releasing the bus:

```
START -> address+W -> register address -> REPEATED START -> address+R -> data in -> STOP
```

**This is the hardest function in the assignment.** On this MCU's I2C peripheral, the end of a read
is genuinely awkward: the peripheral has a two-stage pipeline (a data register and a shift
register), so the NACK for the final byte has to be set up *before* that byte has finished arriving.
The reference manual's "Master receiver" section gives three separate procedures:

- **1 byte** — NACK is configured before clearing the address flag.
- **2 bytes** — needs the POS bit set before clearing the address flag. A distinct procedure, not a
  simplification of the third.
- **3 or more bytes** — read down to the last three, then use BTF to sequence the final bytes.

Implement all three. Dispatch on `len`.

> **Defect to fix:** the code in git history handles `len == 1` and `len >= 3`, but its loop is
> `while (size > 3)` followed by an unconditional read of three bytes. Pass it `len == 2` and it
> **writes three bytes into a two-byte buffer**. It never showed up because the only caller passed
> 14. A general-purpose bus driver gets called with 2 constantly — any 16-bit register pair. Handle
> `len == 0`, `len == 1` and `len == 2` explicitly.

- [ ] **Done when:** reads of 1, 2, 3 and 14 bytes all return correct data, and a read from an
      address with no device returns `DRV_ERR_NACK` or `DRV_ERR_TIMEOUT` within the timeout.

### A6 — Error translation

Implement `I2C_TranslateError()`.

Map the peripheral's error flags onto status codes:

| Condition | Return |
|---|---|
| Acknowledge failure | `DRV_ERR_NACK` |
| Bus error, arbitration lost, overrun | `DRV_ERR_BUS` |
| No error flag set | `DRV_OK` |

**Clear the flags before returning.** A latched error flag will wedge the next transfer, and the
symptom — "the first read works and everything after fails" — looks nothing like the cause.

Then use this function in A4 and A5: check for errors inside the wait loops, not just timeouts.

- [ ] **Done when:** reading from an absent device returns `DRV_ERR_NACK` specifically, and the
      *next* read from a device that is present still succeeds.

### A7 — Audit your wait loops

Search your own file:

```bash
grep -n "while" DRIVERS/src/bus_i2c.c
```

Every single loop must be able to exit on both a timeout and an error flag.

> **Defect to fix:** every wait in the git-history version is an unbounded `while (!flag);`. One
> missing pull-up and the firmware hangs forever with no diagnostic. Later in this project the same
> loop will be running while a propeller spins, which is why this is a rule and not a preference.

- [ ] **Done when:** no unbounded flag-polling loop remains in the file.

## Part B — MPU-6050 library (`DRIVERS/src/mpu6050.c`)

This part contains no MCU-specific code. It talks to the device only through `dev->bus`, which means
you can be confident that any bug here is a *sensor* bug, not a *bus* bug — provided Part A is
finished and tested first. **Do not start Part B until Part A works.**

### B1 — Build the register table

From the register map document, write `#define`s at the top of `mpu6050.c` for every register you
will touch. At minimum you need: the identity register, the power management register, the two
range-configuration registers, the filter configuration register, the sample-rate divider, and the
first register of the measurement block.

Keep them in the `.c` file. Nothing outside this driver should know register addresses.

- [ ] **Done when:** the register table is written and each entry has the register's name from the
      document as a comment.

### B2 — Register access helpers

Implement `MPU6050_ReadRegs()` and `MPU6050_WriteReg()`.

These are thin wrappers. Each one calls through `dev->bus`, filling in `dev->cfg.i2c_addr` and
`dev->cfg.timeout_ms` so the rest of the file reads as register operations rather than bus
operations.

Guard against `dev->bus.read` or `dev->bus.write` being NULL — return `DRV_ERR_PARAM`.

- [ ] **Done when:** both compile and the rest of the file can be written in terms of registers.

### B3 — Probe

Implement `mpu6050_probe()`.

Read the identity register and compare it against the value the register map documents.

| Result | Return |
|---|---|
| Value matches | `DRV_OK` |
| Something responded, wrong value | `DRV_ERR_ID` |
| Nothing responded | whatever the bus returned (`DRV_ERR_NACK`) |

**This is your first real hardware test.** Get it working before writing anything else — it proves
wiring, pull-ups, address, and your entire Part A in one call.

> If it returns `DRV_ERR_NACK`, the problem is the address or the wiring, not this function. Try the
> other AD0 address. If it returns `DRV_ERR_ID`, you are talking to *something* — check you are
> reading the right register.

- [ ] **Done when:** `mpu6050_probe()` returns `DRV_OK` against the real sensor.

### B4 — Initialisation

Implement `mpu6050_init()`.

1. Validate all three pointers. Return `DRV_ERR_PARAM` on NULL.
2. Copy `bus` and `cfg` into the handle. Zero the calibration struct.
3. Bring the device out of its reset power state.
4. Select a clock source. The reset default is not the recommended one — the register map says which
   is preferred and why.
5. Apply `cfg->accel_fs`, `cfg->gyro_fs` and `cfg->dlpf`.
6. Compute and write the sample-rate divider to get as close to `cfg->sample_rate_hz` as possible.
   **The divider divides a base rate that depends on your DLPF setting** — read that register's
   description carefully, it catches people out.
7. Set `initialised = true`.

If any step fails, return that failure and leave `initialised` false.

**Write a short note in [driver_development_log.md](../driver_development_log.md)** listing every
register you did *not* write, and what reset value the device is therefore using. Inheriting a
default silently is still a decision — this is just making it visible.

- [ ] **Done when:** init returns `DRV_OK`, and reading back the configuration registers shows the
      values you intended.

### B5 — Raw read

Implement `mpu6050_read_raw()`.

One burst read of `MPU6050_BURST_LEN` bytes starting at the first measurement register, then
assemble the 16-bit values.

Two things to be careful about:

- The device transmits **most significant byte first**. The MCU is little-endian. You cannot
  `memcpy` the buffer into the struct; assemble each value explicitly with shifts.
- Subtract `dev->cal.gyro_bias` from the gyro values, but **only if `dev->cal.valid`** is set.

- [ ] **Done when:** with the sensor sitting flat and still, one axis of `accel` reads roughly ±1 g
      worth of counts and the other two read near zero.

### B6 — Unit conversion

Implement `MPU6050_AccelScale()`, `MPU6050_GyroScale()` and `mpu6050_convert()`.

The scale factors for each full-scale range are in the product specification (the PDF you already
have), in the electrical characteristics table — look for sensitivity, in LSB per g and LSB per
degree/second.

`mpu6050_convert()` must stay a **pure function**: no bus access, no side effects. That is what lets
you test the arithmetic without hardware.

Temperature has its own formula in the register map. It is an offset-and-scale, not a plain
division.

- [ ] **Done when:** flat and still, the magnitude of the acceleration vector
      `sqrt(x² + y² + z²)` reads within a few percent of 1.0 g.

### B7 — Gyroscope calibration

Implement `mpu6050_calibrate_gyro()`.

1. Take `samples` readings, summing each gyro axis.
2. **While sampling, verify the device is actually still.** Track the minimum and maximum of each
   axis. If the spread on any axis exceeds a threshold you choose, the device moved — return
   `DRV_ERR_STATE` and leave the existing calibration untouched.
3. Store the averages in `dev->cal.gyro_bias`, record the current temperature in
   `dev->cal.temp_c_at_cal`, and set `valid = true`.

**Why the motion check matters:** a bias captured while the device was nudged is silently wrong and
persists into every subsequent reading. Averaging harder does not detect it; only checking the
spread does.

- [ ] **Done when:** after calibration, a still sensor reports gyro rates near zero on all three
      axes, and deliberately nudging the sensor during calibration causes it to return
      `DRV_ERR_STATE`.

## Part C — Test application and verification

### C1 — Create the test app

Create `APPS/src/imu_test.c` and `APPS/inc/imu_test.h` exposing `imu_test_init(void)` and
`imu_test_loop(void)`. Follow the pattern in `APPS/src/blinky.c`.

The app owns the hardware choices — this is the layer that is allowed to know which peripheral the
sensor sits on:

```c
#include "pin_definitions.h"   /* IMU_I2C, IMU_I2C_PORT, IMU_I2C_SCL_PIN, ... */
#include "bus_i2c.h"
#include "mpu6050.h"

static i2c_bus_t s_bus;
static mpu6050_t s_imu;
```

In `imu_test_init()`: fill in the bus configuration fields from `pin_definitions.h`, call
`i2c_bus_init()`, build the transport with `i2c_bus_transport()`, then `mpu6050_init()`,
`mpu6050_probe()` and `mpu6050_calibrate_gyro()`. Report each step over USART.

Then register it:

1. Add `#define APP_IMU_TEST` to `APPS/inc/app_selector.h`, and comment out `APP_BLINKY`.
2. Add the two `#ifdef` blocks in `APPS/src/main_app.c`.
3. **Re-run CMake configure**, not just build — sources are globbed:
   ```bash
   cmake --preset NUCLEO-F401RE-Debug-Local
   ```

- [ ] **Done when:** the app builds and prints the result of each init step over the serial port.

> **API check:** if you find yourself needing something the driver headers do not expose, stop and
> write down what it was. That is a finding about the API design, and it is worth more than working
> around it.

### C2 — Verification ladder

Work down this list in order. Each rung catches bugs the one before it cannot.

- [ ] Identity register returns the expected device ID
- [ ] At rest, acceleration magnitude ≈ 1 g in **any** static orientation — not just flat. A single
      orientation cannot distinguish a scaling error from an axis-assignment error
- [ ] Six-face test: each axis reads +1 g pointing up and −1 g pointing down
- [ ] Gyro reads ≈ 0 at rest after calibration
- [ ] Rotate the sensor a deliberate 90° and integrate the gyro rate over the motion — the result
      should land near 90°
- [ ] Sign convention confirmed: a positive reading on each axis means what you expect it to mean.
      Write down the convention you observed
- [ ] Measure the real sample interval — toggle a GPIO in the loop and scope it, or timestamp on the
      host. Do not trust the nominal rate

### C3 — Failure-mode testing

A driver whose error paths have never executed is a driver whose error paths do not work. Provoke
each of these deliberately:

- [ ] Disconnect SDA mid-run — the driver reports an error and does not hang
- [ ] Reconnect it — the driver recovers, either on its own or after a re-init
- [ ] Power-cycle the sensor while the MCU keeps running — the driver notices
- [ ] Reset the MCU mid-transfer, repeatedly — this is the exact scenario `i2c_bus_recover()` exists
      for, so it is the one case where you must see it work

### C4 — Measure the cost

Time one `mpu6050_read_raw()` call. Use the Cortex-M4 cycle counter (`DWT->CYCCNT`) or toggle a GPIO
around the call and scope it.

Record two numbers in the log: the duration at 100 kHz, and at 400 kHz (change the `speed` argument
to `i2c_bus_init`). The eventual control loop runs at 250 Hz — a 4 ms budget.

- [ ] **Done when:** both numbers are written down in
      [driver_development_log.md](../driver_development_log.md), along with what fraction of 4 ms
      each represents.

This measurement decides whether Assignment 02 is worth doing at all. Do not skip it.

## Appendix — Common failure modes

| Symptom | Most likely cause |
|---|---|
| Every transfer times out immediately | Peripheral never enabled — `MX_I2C1_Init()` leaves it disabled |
| Nothing responds, SDA stuck low | Bus wedged. Run recovery. Check pull-ups exist |
| Probe returns `DRV_ERR_NACK` | Wrong address, or address shifted twice. `dev_addr` is 7-bit right-aligned; shift in exactly one place |
| First read works, everything after fails | A latched error flag was never cleared |
| Data is byte-swapped garbage | Device sends MSB first; you assembled it little-endian |
| Accel magnitude is 2× or 0.5× correct | Scale factor does not match the configured range |
| Values look right but drift steadily | Gyro bias not applied, or calibration ran while moving |
| Sample rate is not what you asked for | The divider's base rate depends on the DLPF setting |
| Reads of 2 bytes corrupt memory | The `len == 2` case — see A5 |
| Firmware hangs with no output | An unbounded wait loop — see A7 |
