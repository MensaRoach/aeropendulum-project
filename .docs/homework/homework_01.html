S3

Wire the sensor

~20 min

I2C1 is on PB6 (SCL) and PB7 (SDA). Power the sensor from 3.3 V and share ground with the Nucleo.

Check whether your breakout already carries pull-up resistors on SDA and SCL — most do. If it does not, fit 4.7 kΩ from each line to 3.3 V. I2C cannot work without them: the pins only ever pull low, and something has to pull them back up.

Part A · 3 tasks

First light: talking to the host

Before anything else, give yourself eyes. The USART is the simplest peripheral on this board, and by the end of these three tasks you can print from the firmware to a terminal on your laptop.

Why this comes first

Part B is the hardest thing in the assignment, and debugging it blind is miserable. An hour spent here buys you a printf for the rest of the project. It also teaches the timeout pattern and the drv_status_t discipline on a peripheral simple enough that those ideas are the only new thing.

A1

A deadline you can trust

~45 min

Every blocking call in this project takes a timeout, so every one of them needs to answer the question “has long enough passed?”. Write a small static helper: 

static bool DeadlineExpired(uint32_t start_ms, uint32_t timeout_ms);

SysTick already runs at 1 kHz — see LL_Init1msTick in SystemClock_Config. LL exposes a tick counter you can read.

Write it in bus_uart.c now. You will need the same logic in bus_i2c.c in Part B, where it is already declared for you as I2C_DeadlineExpired().

Trap

The tick counter is a uint32_t and eventually wraps back to zero. Subtracting unsigned values in the right order handles the wrap correctly; comparing them with > does not, and the bug appears once every 49 days — which is to say, in the field.

Hint — about the duplication

Yes, you will end up with near-identical helpers in two files. That is the right call for two — a shared timing header earns its place at three. Note the decision in driver_development_log.md so the next person knows it was a choice rather than an oversight.

Done when

Returns false immediately after start_ms and true once the timeout has passed — including across a counter wrap. Test the wrap by passing a start_ms near UINT32_MAX.

A2

USART initialisation

~30 min

Implement uart_bus_init().

  1. Validate bus and bus->instance. Return DRV_ERR_PARAM if either is NULL.
  2. Clear the private fields.
  3. Work out whether there is anything left to do — see below.
  4. Set initialised = true and return DRV_OK.
Do not assume — go and look

In Part B you will find that the generated I2C setup leaves its peripheral disabled. It would be reasonable to assume the USART behaves the same way. Open BOARDS/NUCLEO-F401RE/Core/Src/usart.c (F407 note: The .ioc doesn't include USART yet, so you are using identical placeholder files for now), read the end of MX_USART2_UART_Init(), and find out rather than guessing.

Two peripherals configured by the same tool in the same project do not necessarily leave you in the same state. Write down what you found.

Done when

Init returns DRV_OK, and you can say in one sentence why it does or does not need to enable the peripheral.

A3

Blocking transmit

~1.5 h

Implement uart_bus_write(). For each byte:

  1. Wait until the transmit data register is empty (TXE).
  2. Write the byte.

After the last byte, wait for TC — transmission complete.

TXE and TC are not the same thing

TXE means “the holding register is free, give me the next byte”. TC means “the last bit has actually left the pin”. Return on TXE and the final character may still be in flight — which is how you lose the last few characters of a message when the board resets right after printing it.

Every wait uses your DeadlineExpired() from A1 and returns DRV_ERR_TIMEOUT rather than spinning forever.

Hint — getting a terminal open

USART2 is routed to the ST-LINK virtual COM port, so it appears as a serial device when you plug the board in (F407 note: ST-LINK VCP routing on the DISC1 might require a USB-TTL adapter depending on board revision): COM* on Windows, /dev/cu.usbmodem* on macOS, /dev/ttyACM* on Linux. Settings are 115200 8E1 — note the E: even parity, not the more common 8N1. Set that wrong and you get plausible-looking garbage rather than silence, which is worse.

Done when

A short test app sends "hello\r\n" through uart_bus_write() and it appears intact in your terminal — every character, every time, including the last one.

Part B · 6 tasks

I2C bus driver

No sensor-specific behaviour appears anywhere in this part. You are building a general-purpose I2C register read and write for the STM32F4 that would work with any device on the bus. This is the hard half of the assignment.

Why the order matters

Finish and test Part B before touching Part C. Once the bus is known-good, every bug you meet in Part C is provably a sensor bug, not a bus bug. That halves the search space at exactly the point where it gets confusing.

B1

Bus recovery

~2 h

Implement i2c_bus_recover().

Why it exists: if the MCU resets midway through a read, the sensor is left part-way through transmitting a byte, holding SDA low and waiting for clock pulses that will never arrive. The bus is stuck before the peripheral is even switched on, and no amount of peripheral configuration will free it. The only escape is to drive the pins by hand.

  1. Reconfigure scl_pin and sda_pin as general-purpose open-drain outputs with pull-ups.
  2. Drive both high, wait briefly.
  3. Toggle SCL up to nine times. After each pulse, check whether SDA has gone high — stop as soon as it has.
  4. Generate a manual STOP: SDA low, then SCL high, then SDA high.
  5. Return both pins to alternate-function mode using bus->gpio_af.
Hint — why nine, and why open-drain

Nine because a byte is eight bits plus an acknowledge: nine clocks guarantees the slave finishes whatever byte it was in the middle of and lets go. Open-drain because on I2C nobody ever drives a line high — devices only pull low, and the pull-up resistors do the rest. Drive it high as a push-pull output and two devices can fight, which is a short circuit rather than a protocol.

Design requirement

Check whether recovery actually worked and report it. A routine that clocks nine times and returns success regardless is a ritual, not a fix.

Done when

Returns DRV_OK if SDA is high at the end, and DRV_ERR_BUS if it is still low after nine pulses.

B2

Initialisation

~1 h

Implement i2c_bus_init(), and copy your A1 deadline helper into the body of I2C_DeadlineExpired(), which is already declared at the top of the file.

The thing everyone misses

MX_I2C1_Init() configures the peripheral — timing, addressing mode, duty cycle — and then leaves it disabled. LL_I2C_Init() ends with a call to LL_I2C_Disable() and never re-enables it. Switching it on is your job, and if you skip it every single transfer times out with no other symptom.

  1. Validate bus and bus->instance. Return DRV_ERR_PARAM if either is NULL.
  2. Call i2c_bus_recover(). On failure, return that failure and leave initialised false.
  3. If speed differs from what CubeMX programmed, reconfigure it. Look at LL_I2C_ConfigSpeed.
  4. Enable the peripheral.
  5. Clear busy, set initialised = true, return DRV_OK.

Done when

A failed init leaves initialised false, and every transfer function returns DRV_ERR_STATE while it stays false. Add that guard to each transfer function as you write it.

B3

Blocking write

~2 h

Implement i2c_bus_write(). The transaction you are producing:

START → address+W → register address → data[0] … data[len-1] → STOP

The flags involved are SB, ADDR, TXE and BTF. The master-transmitter flowchart in RM0368 gives their exact order — work from that, not from guesswork.

Requirements specific to this codebase:

  • bus arrives as void * because the transport interface is deliberately type-agnostic. Cast it to i2c_bus_t * on the first line.
  • dev_addr is 7-bit and right-aligned. Shift it and add the read/write bit here, in exactly one place in the whole codebase.
  • Timestamp at the top. Every wait loop tests I2C_DeadlineExpired() and returns DRV_ERR_TIMEOUT instead of spinning forever.
  • Set busy on entry and clear it on every exit path, including the error ones.
  • Return DRV_ERR_PARAM for NULL data with non-zero len.
Hint — clearing ADDR

The ADDR flag is not cleared by writing to it. It clears as a side effect of reading SR1 and then SR2, in that order. Miss this and the peripheral stalls with the flag still set, which looks exactly like the device not responding.

Done when

Writing to an address with nothing on it returns an error inside the timeout instead of hanging, and writing to the real sensor returns DRV_OK. You can print both outcomes using Part A.

B4

Blocking read

~4 h

Implement i2c_bus_read(). This is the hardest function in the assignment — give it a whole sitting, and expect the first version to be wrong.

A register read is a combined transfer: the direction reverses mid-transaction without ever releasing the bus.

START → address+W → register address
      → REPEATED START → address+R → data in → STOP

The tail of a read is genuinely awkward on this peripheral. It has a two-stage pipeline — a data register behind a shift register — so the NACK that terminates the read must be set up before the final byte has finished arriving. That timing constraint is why the reference manual gives three separate procedures:

LengthWhat makes it different
len == 1 NACK is configured before the ADDR flag is cleared.
len == 2 Requires the POS bit set before ADDR is cleared. A distinct procedure, not a simplification of the third.
len >= 3 Read down to the final three bytes, then use BTF to sequence the last of them.

Implement all three and dispatch on len.

Requirement

Handle len == 0, 1 and 2 explicitly. It is tempting to write the len >= 3 case and treat the others as edge cases of it — that produces a function which writes three bytes into a two-byte buffer. A general-purpose bus driver gets called with len == 2 constantly, for any 16-bit register pair.

Hint — a sane order to build this in
  1. Write the len == 1 case first and test it against a single register. Shortest path to something that works.
  2. Then len >= 3, tested with a 6-byte read.
  3. Then len == 2 last, because it is the fiddliest and you will want the other two working as a reference.
  4. Then len == 0, which should simply return DRV_ERR_PARAM without touching the bus.

Done when

Reads of 1, 2, 3 and 14 bytes all return correct data, and a read from an address with no device returns DRV_ERR_NACK or DRV_ERR_TIMEOUT inside the timeout.

B5

Error translation

~1 h

Implement I2C_TranslateError().

ConditionReturn
Acknowledge failureDRV_ERR_NACK
Bus error, arbitration lost, overrunDRV_ERR_BUS
No error flag setDRV_OK
Clear the flags

A latched error flag wedges the next transfer. The symptom — “the first read works and everything after it fails” — looks nothing like the cause, and people lose days to it.

Then go back into B3 and B4 and check for errors inside the wait loops, not just timeouts. A missing device should surface as DRV_ERR_NACK immediately, not as a full timeout — the difference between a diagnosis and a shrug.

Done when

Reading from an absent device returns DRV_ERR_NACK specifically and quickly, and the next read from a device that is present still succeeds.

B6

Busy flag and wait-loop audit

~45 min

Implement i2c_bus_is_busy() — it reports bus->busy, guarding against a NULL pointer.

Worth noticing

This is the one function in the whole driver set that cannot report an error, because it returns bool. Its stub returned false — a confident, specific, wrong answer that no caller could distinguish from the truth. Every other stub in this project returns DRV_ERR_STATE precisely so it cannot do that. Keep the observation in mind whenever you are tempted to return a bare bool from something that can fail.

Then audit your own file:

grep -n "while" DRIVERS/stm32f4/src/bus_i2c.c DRIVERS/stm32f4/src/bus_uart.c

Every loop must be able to exit on both a timeout and an error flag. Not one or the other.

Why this is a rule and not a preference

A single missing pull-up turns an unbounded while (!flag); into a permanent hang with no diagnostic. Later in this project the same loop runs while a propeller is spinning. A firmware hang is a safety failure at that point, not an inconvenience.

Done when

i2c_bus_is_busy() reports the real state, and no unbounded flag-polling loop remains in either driver file.

Part C · 7 tasks

MPU-6050 library

No MCU-specific code appears in this part. The driver reaches the device only through dev->bus, which is what makes it portable — and what makes its bugs easy to isolate, provided Part B is finished.

C1

Build the register table

~1 h

From the register map document, write #defines at the top of mpu6050.c for every register you will touch. At minimum:

  • the identity register
  • the power management register
  • the two range-configuration registers
  • the filter configuration register
  • the sample-rate divider
  • the first register of the measurement block

Keep them in the .c file. Nothing outside this driver has any business knowing a register address — that is exactly the knowledge the header exists to hide.

Done when

The table is written, and each entry carries the register's name from the document as a comment.

C2

Register access helpers

~45 min

Implement MPU6050_ReadRegs() and MPU6050_WriteReg().

Thin wrappers. Each calls through dev->bus, filling in dev->cfg.i2c_addr and dev->cfg.timeout_ms so the rest of the file reads as register operations rather than bus operations.

Guard against dev->bus.read or dev->bus.write being NULL — return DRV_ERR_PARAM. A caller who forgot to bind the transport deserves an error, not a crash at address zero.

Done when

Both compile, and the rest of the file can be written in terms of registers.

C3

Probe

~1 h

Implement mpu6050_probe(). Read the identity register and compare against the value the register map documents.

ResultReturn
Value matchesDRV_OK
Something answered, wrong valueDRV_ERR_ID
Nothing answeredwhatever the bus returned
Milestone — the best moment in the assignment

This is the first time the sensor answers you by name, and it validates wiring, pull-ups, address and the whole of Part B in a single call. Get it green before writing anything else.

Hint — reading the result
  • DRV_ERR_NACK means the address or the wiring is wrong, not this function. Try the other AD0 address.
  • DRV_ERR_ID means you are talking to something — check you are reading the register you think you are.
  • A timeout points back at Part B, not at the sensor.

Done when

mpu6050_probe() returns DRV_OK against the real sensor.

C4

Initialisation

~2 h

Implement mpu6050_init().

  1. Validate all three pointers. DRV_ERR_PARAM on NULL.
  2. Copy bus and cfg into the handle. Zero the calibration struct.
  3. Bring the device out of its reset power state.
  4. Select a clock source. The reset default is not the recommended one — the register map says which is preferred and why.
  5. Apply cfg->accel_fs, cfg->gyro_fs and cfg->dlpf.
  6. Compute and write the sample-rate divider to land as close to cfg->sample_rate_hz as possible.
  7. Set initialised = true.
Trap in step 6

The divider divides a base rate that depends on your DLPF setting. Read that register's description carefully. Getting this wrong gives you a sample rate that is silently eight times what you asked for — and everything still looks like it works.

Write-up

Add a note to driver_development_log.md listing every register you did not write, and the reset value the device is therefore using. Inheriting a default is still a decision — this just makes it a visible one.

Done when

Init returns DRV_OK, and reading the configuration registers back shows the values you intended. Read them back — do not assume the write landed.

C5

Raw read

~1.5 h

Implement mpu6050_read_raw(): one burst read of MPU6050_BURST_LEN bytes starting at the first measurement register, then assemble the 16-bit values.

  • The device transmits most significant byte first; this MCU is little-endian. You cannot memcpy the buffer into the struct — assemble each value explicitly with shifts.
  • Subtract dev->cal.gyro_bias, but only if dev->cal.valid is set.
Hint — why one burst and not seven reads

The seven values are latched together, so a single burst gives you one coherent instant. Seven separate reads sample seven slightly different moments, and the resulting accelerometer vector belongs to no actual orientation the board was ever in.

Done when

With the sensor flat and still, one accelerometer axis reads roughly ±1 g worth of counts and the other two sit near zero.

C6

Unit conversion

~1 h

Implement MPU6050_AccelScale(), MPU6050_GyroScale() and mpu6050_convert().

The scale factors for each full-scale range are in the product specification — the PDF you already have — in the electrical characteristics table. Look for sensitivity, given in LSB per g and LSB per degree-per-second.

mpu6050_convert() must stay a pure function: no bus access, no side effects. That is what lets you test the arithmetic with made-up numbers, at your desk, with no hardware attached.

Temperature has its own formula in the register map. It is an offset-and-scale, not a plain division.

Done when

Flat and still, the magnitude of the acceleration vector sqrt(x² + y² + z²) reads within a few percent of 1.0 g.

C7

Gyroscope calibration

~1.5 h

Implement mpu6050_calibrate_gyro().

  1. Take samples readings, summing each gyro axis.
  2. While sampling, verify the device is genuinely still. Track the minimum and maximum of each axis. If the spread on any axis exceeds a threshold you choose, it moved — return DRV_ERR_STATE and leave the existing calibration untouched.
  3. Store the averages in dev->cal.gyro_bias, record the current temperature in dev->cal.temp_c_at_cal, and set valid = true.
Why step 2 matters

A bias captured while the sensor was nudged is silently wrong, and it persists into every reading afterwards. Averaging over more samples does not detect it — more samples just gives you a more confident wrong answer. Only checking the spread does.

Hint — why temperature is recorded

Gyroscope bias drifts with temperature, and the sensor warms up for a few minutes after power-on. A calibration taken cold does not describe the device once it is warm, which is why the struct has somewhere to put the temperature. You are not required to act on it in this assignment — only to capture it, so a later you can.

Done when

After calibration a still sensor reports near-zero rates on all three axes — and deliberately nudging it during calibration causes DRV_ERR_STATE.

D4

Measure the cost

~1 h

Time one mpu6050_read_raw() call. Use the Cortex-M4 cycle counter (DWT->CYCCNT), or toggle a GPIO around the call and scope it.

Part E · 3 tasks

Integrate

The payoff of building this as LIB/ + DRIVERS/<family>/ instead of one board-specific blob. If the layering is real and not just a diagram, your driver runs on your partner's board with zero changes.

Why this is the real test

Both of you wrote the whole thing independently. A code review can tell you whether a merge looks right. It cannot tell you whether a board-specific assumption is quietly baked into what is supposed to be portable code — a hard-coded clock value, a pin number, an instance that only happens to exist on one of the two boards. Only running it on hardware neither of you originally targeted can catch that.

E1

Merge and synthesise

~2 h, together

You each have a complete, independently-written DRIVERS/stm32f4/ and LIB/mpu6050/. Sit down together and produce one merged branch.

This is not mechanical conflict resolution — there is no shared ancestor for these files, so every difference is a real choice between two working approaches. For each one:

  1. Read both versions of the function side by side (git diff <branch-a>..<branch-b> -- <path> is a fast way to see them together).
  2. Pick the clearer one, or combine the best parts of both.
  3. If they disagree on behaviour and not just style — a different timeout value, a different error code for the same failure — that disagreement is worth a sentence in the log, because it means one of you found something the other missed.
After merging

Both of you reset your own branch onto the merged result before continuing. Skip this and your branches silently diverge again, and the next merge re-fights everything this one just settled.

Done when

One branch builds clean on the board you developed on, and every difference between the two originals was a deliberate choice, not an accident of whoever's merge happened to win.

E2

Cross-flash

~1 h, together

Take the merged branch from E1. Build it against the board you did not develop on and flash it there. 

cmake --preset <their-board>-Debug-Local
cmake --build .build/<their-board>-Debug-Local

Run the verification ladder from D2 again, in full, on that board. Not a glance at the LED — the whole ladder, including the six-face test.

If it does not just work

Good — you found the thing this task exists to find. Somewhere a board-specific assumption leaked into code that was supposed to be portable. Common culprits: a clock value that should have come from PCLK1 at runtime instead of being written down as a constant, a pin or instance macro used directly instead of through pin_definitions.h, or a timing constant tuned for one board's bus speed. Fix it in the shared branch, not with a board-specific #ifdef — an #ifdef here is a patch over the leak, not a fix of it.

Done when

The merged driver passes the full D2 ladder on both boards from the same source tree, with no board-specific code path in DRIVERS/stm32f4/ or LIB/mpu6050/.

E3

Record what you found

~30 min

When stuck

Symptoms and their usual causes. Check here before rewriting anything.

SymptomMost likely cause
Serial output is garbage, not silenceTerminal set to 8N1. The port is 8E1 — even parity — see A3
Last characters of a message go missingReturned on TXE instead of waiting for TC — see A3
Every I2C transfer times out immediatelyPeripheral never enabled. MX_I2C1_Init() leaves it disabled — see B2
Nothing responds, SDA stuck lowBus wedged. Run recovery. Confirm pull-ups exist
Probe returns DRV_ERR_NACKWrong address, or the address got shifted twice. dev_addr is 7-bit right-aligned; shift in exactly one place
First read works, everything after failsA latched error flag was never cleared — see B5
Data is byte-swapped garbageDevice sends MSB first; you assembled it little-endian — see C5
Accel magnitude is 2× or 0.5× correctScale factor does not match the configured range — see C6
Values look right but drift steadilyGyro bias not applied, or calibration ran while moving
Sample rate is not what you asked forThe divider's base rate depends on the DLPF setting — see C4
Reads of 2 bytes corrupt memoryThe len == 2 case was folded into len >= 3 — see B4
