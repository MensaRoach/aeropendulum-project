# Aeropendulum Project

This is a hobby embedded systems project to create an Aeropendulum. The project is designed to be highly portable across Windows and macOS, using VS Code as the development environment and STM32CubeCLT as the toolchain.

## Directory Structure

* **`LIB/`** - Portable device drivers and shared abstractions. Code here compiles against no STM32 headers — portability is enforced at build time. `LIB/drv_common/` holds shared type and interface headers; `LIB/mpu6050/` holds the MPU-6050 driver. See [LIB/README.md](LIB/README.md).
* **`BOARDS/`** - Contains board-specific configurations generated by STM32CubeIDE. Each board has its own subfolder (e.g., `NUCLEO-F401RE`, `STM32F407G-DISC1`) with a `board.cmake` manifest and `pin_definitions.h`. We use STM32 Low-Level (LL) drivers for efficiency.
* **`APPS/`** - Application code, wiring and control logic. Compiles into the static library `apps`.
* **`DRIVERS/`** - Platform drivers keyed by MCU family. `DRIVERS/stm32f4/` holds the STM32F4 I2C and USART drivers, shared by both the F401 and F407 boards. Compiles into the static library `drivers`. See [DRIVERS/README.md](DRIVERS/README.md) for the layering rule.
* **`.cmake/`** - Contains the custom CMake toolchain (`gcc-arm-none-eabi.cmake`), CPU profile flag mappings (`cortex_profiles.cmake`), and multi-board scripts (`stm32.cmake`).
* **`.docs/`** - Component datasheets, MCU reference manuals, and the project's own design writeups.
* **`tools/`** - Host-side Python for reading and visualizing the board's telemetry.
* **`.build/`** - Build output directory.

## Project Status

Two people are now working on this project with different boards:
the repo owner on a **NUCLEO-F401RE** (STM32F401RET6, 84 MHz) and a collaborator on a
**STM32F407G-DISC1** (STM32F407VGT6, 168 MHz). Both are STM32F4, so they share one
`DRIVERS/stm32f4/` platform layer. The collaborator's board is tracked but does not
yet have USART configured — see `BOARDS/STM32F407G-DISC1/pin_definitions.h`.

The firmware currently on the board is a blinky and a USART "hello" demo. The MPU6050 driver was
deliberately deleted to be rewritten from scratch as a learning exercise; `LIB/mpu6050/` and
`DRIVERS/stm32f4/` hold the scaffold for that rewrite — **interfaces and contracts only, no
implementation**. There is no sensor acquisition, no motor drive and no control loop yet.

See [.docs/driver_development_plan.md](.docs/driver_development_plan.md) for what is being built and
in what order, and [.docs/feasibility_analysis.md](.docs/feasibility_analysis.md) for the hardware
analysis — including the safety section, which is worth reading before anything is powered.

## Prerequisites

1. **STM32CubeCLT** installed on your system.
2. **VS Code** with CMake Tools extension.

## Getting Started

To ensure cross-platform compatibility without overwriting each other's paths, this project uses `CMakeUserPresets.json`. 

1. Create a `CMakeUserPresets.json` file in the root directory (this file is ignored by Git).
2. Define a `local-toolchain` base preset with the `PATH` to your STM32CubeCLT installation, and inherit from it.

### Building the Project

Configure and build for your target board using the local preset:

```bash
cmake --preset NUCLEO-F401RE-Debug-Local
cmake --build .build/NUCLEO-F401RE-Debug-Local
```

If the toolchain is already on your system `PATH` (e.g. installed via Homebrew on macOS):

```bash
cmake --preset NUCLEO-F401RE-Debug
cmake --build .build/NUCLEO-F401RE-Debug
```

## Adding a Board

1. Generate the board in STM32CubeIDE with **LL drivers**. Copy the export to `BOARDS/<board>/`. (Never use the CubeMX CMake generator — see repo conventions).
2. Write `BOARDS/<board>/board.cmake` and `BOARDS/<board>/pin_definitions.h`.
3. Add the hidden preset, two concrete presets, and two build presets to `CMakePresets.json`.
4. Add a `.vscode/launch.json` configuration with that board's `device`.
5. Build with `cmake --preset <board>-Debug && cmake --build .build/<board>-Debug`.

## Host Tools

The scripts in `tools/` read the board's telemetry stream over the ST-LINK virtual COM port.

> **These currently have nothing to read.** The firmware that emitted telemetry was deleted along
> with the MPU6050 driver. The tools were kept because they define the wire format a replacement
> driver has to match: a packed 14-byte payload (7 × `int16_t` — ax, ay, az, temp, gx, gy, gz,
> little-endian), COBS-encoded, `0x00`-delimited, at **115200 8E1**. Open the port with
> `PARITY_EVEN` or every frame fails to decode. `out.txt` in the repo root is a captured sample
> session showing expected output.

Set up a virtual environment and install the dependencies:

```bash
python -m venv .venv
```

Activate it (`\.venv\Scripts\activate` on Windows, `source .venv/bin/activate` on macOS/Linux), then:

```bash
pip install -r tools/requirements.txt
```

Find the board's port and start the reader:

* **Windows** — a `COM*` port, listed by `mode` or in Device Manager.
* **macOS** — `ls /dev/cu.usbmodem*`. Use the `cu.` device, not `tty.`; the `tty.` device blocks
  waiting for carrier detect. No driver install is required.
* **Linux** — `/dev/ttyACM*`. You may need to add yourself to the `dialout` group.

```bash
python tools/read_telemetry.py -p /dev/cu.usbmodem1103
```

`tools/visualize_imu.py` renders live 3D orientation, and `tools/imu_music/main.py` drives a
synthesizer from the IMU (run that one from inside its own directory — it uses flat imports).

## Contributing

When generating new code via STM32CubeIDE, ensure you are generating **LL (Low Level)** drivers, not
HAL — and never use the CubeMX CMake generator, which would break this project's own CMake wrapper.

Keep custom code out of the generated files. The only intended edits inside `BOARDS/` are the
existing `app_main()` call in `main.c` and driver IRQ hooks placed in the `USER CODE` blocks of
`stm32f4xx_it.c`. Everything else goes in:

* **`DRIVERS/`** — anything that talks to hardware registers, or to a device over a bus.
* **`APPS/`** — application logic, and the wiring that decides which peripheral a driver instance uses.

[CLAUDE.md](CLAUDE.md) carries the full conventions, including the driver contract rules
(`drv_status_t` returns, mandatory timeouts, 7-bit I2C addresses).
